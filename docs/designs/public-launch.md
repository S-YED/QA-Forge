## Problem Statement
QA Forge is currently a working MVP-2 codebase but lacks a public, shareable deployment. To demonstrate engineering depth, product thinking, and execution quality to hiring managers, the product needs to be publicly deployed with an interactive, zero-barrier demo.

## Demand Evidence
The project is built to address personal pain and serve as a technical portfolio showcase. Real-world target users (QA leads and solo founders) are currently bogged down by manual testing spreadsheets and custom test scripts that constantly drift.

## Status Quo
Users currently track test suites manually in spreadsheets (Excel or Google Sheets), write test scripts by hand (spending hours debugging locators), or use cobbled internal script runners that fail silently.

## Target User & Narrowest Wedge
- **Target User:** Sarah the Lead QA Engineer, Dave the Solo Developer, and Alex the Engineering Manager.
- **Narrowest Wedge:** A `/demo` route that automatically logs visitors into a read-only guest account (`demo@qaforge.dev`) seeded with rich project history, test suites, and realistic bug records, allowing them to witness visual test execution immediately without sign-up.

## Constraints
- **Timeline:** 1 week sprint.
- **Safety:** Read-only access for guest users to prevent database pollution.
- **Cost:** Avoid runaway OpenAI API token usage from public guest actions.

## Premises
1. QA Forge needs a shareable, publicly deployed live URL to prove engineering depth to hiring managers.
2. The manual spreadsheets, custom scripts, and cobbled internal tools that lead QA teams and solo founders to waste hours can be unified into a transparent, visual AI-driven web test runner.
3. A pre-seeded read-only demo account (demo@qaforge.dev) is the fastest way to showcase value without requiring sign-up or incurring credit costs.

## Approaches Considered

### Approach A: Minimal Viable Deployment & Hardcoded Demo
- **Summary:** Deploy the web frontend and API runner. Hardcode the dashboard states and demo data directly on the client, disabling real database or socket interaction.
- **Effort:** S (human: ~1 day / CC: ~10 min)
- **Risk:** Low
- **Pros:**
  - ✅ Fastest path to a working shareable link.
  - ✅ Minimal server load and zero database corruption risks.
- **Cons:**
  - ❌ UI feels static; cannot trigger live test executions.
  - ❌ Fails to demonstrate full-stack engineering depth.
- **Reuses:** Existing frontend UI layouts.

### Approach B: Full Real-Time Integration & Seeded Database (Recommended)
- **Summary:** Setup Vercel (web) and Railway (API) production deployments. Implement read-only Row Level Security (RLS) policies for the guest account. Seed the database with rich multi-project history, and configure WebSockets for live execution visual updates.
- **Effort:** M (human: ~3 days / CC: ~25 min)
- **Risk:** Med
- **Pros:**
  - ✅ Showcases actual engineering depth with live WebSocket progress streams.
  - ✅ Premium, interactive feel with realistic test logs and visual states.
- **Cons:**
  - ❌ More complex deployment setup involving both Railway API and Supabase migrations.
  - ❌ Requires careful RLS policy testing to prevent guest account data corruption.
- **Reuses:** Existing Express WebSocket socket-server, Playwright runner, and app migration patterns.

### Approach C: Simulated Agentic QA Runner (Creative/Lateral)
- **Summary:** Simulate test execution locally on the client using interactive SVG animations and timed state transitions. Skip backend execution for demo users.
- **Effort:** S (human: ~1.5 days / CC: ~15 min)
- **Risk:** Low
- **Pros:**
  - ✅ Highly visual, animated, and reliable demo that runs fully on the client.
  - ✅ Zero server-side Playwright execution costs or credit consumption.
  - ❌ Simulated runs do not show true backend-level software architecture.
  - ❌ Hiring managers checking network tabs will see mock API responses.
- **Reuses:** Existing Next.js page layouts and frontend context state.

## Recommended Approach
Approach B is chosen because it directly addresses the hiring manager evaluation criteria, demonstrating robust full-stack integration, real-time WebSocket communication, and database security design.
